# CampusFlow backend

Run the FastAPI service from this directory:

```powershell
uv sync
uv run uvicorn app:app --reload
```

Seed the SQLite database with the repeatable synthetic student dataset:

```powershell
uv run python seed_student_data.py
uv run python seed_leave_profiles.py
uv run python seed_marketplace_products.py
```

The API listens on `http://127.0.0.1:8000`. Complaint data is stored in
`complaints.db`. Backend settings are loaded from `backend/.env`, independent
of the directory used to start the server. Configure `CORS_ORIGINS` there when
the frontend uses a different origin. The study assistant requires
`SARAVAM_API`; it is never sent to the frontend. Restart the backend after
changing `.env`.

Available endpoints:

- `GET /api/health`
- `GET /api/students` — list synthetic student records, including subject scores and activities
- `POST /api/students/analytics` — return verified SQLite-based findings with Sarvam-105B educational interpretation
- `POST /api/projects/reports/analyze` — extract PDF/DOCX/TXT report text and return an AI-assisted readiness review
- `GET /api/projects/reports` — list draft or mentor-submitted reports for one project and demo user
- `POST /api/projects/reports/{report_id}/submit` — submit a scored report to the assigned mentor
- `POST /api/projects/reports/{report_id}/mentor-analysis` — generate a separate AI analysis for an incoming mentor report
- `POST /api/study-assistant/chat` — answer a study question using Sarvam-105B
- `GET /api/marketplace/products` — list marketplace listings from SQLite
- `POST /api/marketplace/chat` — recommend matching SQLite listings with Sarvam-105B
- `POST /api/requests/rewrite-description` — improve an OD/leave description with the AI agent
- `POST /api/requests/ai-review` — review an OD/leave request with the Sarvam advisor/HOD assistant and synthetic demo-student performance context
- `GET /api/complaints`
- `POST /api/complaints`
- `DELETE /api/complaints/{complaint_id}` — permanently remove a student complaint marked solved
- `POST /api/complaints/{complaint_id}/escalate`
- `POST /api/complaints/chat`

Complaint submission dates are stored in `user_complaints.complaint_date`.
Existing rows are assigned the migration date when this column is first added;
new complaints receive their current local date. A student can escalate an
unresolved complaint after three calendar days. The escalation report is
generated by a dedicated agent and delivered using the existing complaint
routing agent and configured Pushover credentials. Failed delivery does not
mark the complaint as escalated.

Student analytics uses the synthetic rows in `student_data`. Demo student
profiles `S1`–`S12` are linked to their own seeded rows; faculty and Admin
requests analyze the full dataset. This role scope is for the current
local-storage demo only: the app has no backend authentication, so deployable
student privacy requires authenticated identities enforced by the server.
Analytics are calculated from database records before the educational analyst
agent interprets them. Attendance is not currently stored in `student_data`
and therefore cannot be analyzed by this endpoint. If Sarvam cannot produce
an interpretation, the endpoint still returns the verified database findings
with `interpretationAvailable: false`; the UI displays that limitation rather
than presenting the findings as an AI-generated interpretation. Responses also
include short plain-language notes about how to interpret common metrics and
question-relevant `visualizations` data for the frontend to chart. Charts show
only measures supported by the stored records; they do not imply causation or
replace faculty review.

Project report review accepts PDF, DOCX, and UTF-8 TXT files up to 10 MB.
Uploaded binaries are parsed in memory and are not retained; extracted report
text and AI feedback are stored in `complaints.db` so the assigned mentor can
review submitted documents. The extracted text is sent to Sarvam-105B for both
the student's pre-submission check and the mentor's separate analysis. Readiness
scores use a generic rubric and are advisory; the displayed low/medium/high
revision-risk band maps to scores of 75-100, 50-74, and 0-49 respectively. It
is not a rejection probability, institutional grade, or automated decision.
The report endpoints use the current app's demo role and user IDs, not
authenticated identities; they are suitable only for this local prototype and
must not be used to protect real student documents in production.

The OD/leave AI review uses a separate `demo_leave_student_profiles` SQLAlchemy
table with twelve synthetic demo students. Attendance and CGPA match the
frontend demo profiles; subject scores and activity details are copied from
their seeded synthetic student records. Seed the main student table first,
then run `uv run python seed_leave_profiles.py`. The assistant's 0-100 score
describes how strongly the supplied evidence supports its suggestion; it is
not an approval probability or student eligibility score. Attendance, CGPA,
and other performance data are contextual only and must not independently
determine leave approval. The advisor or HOD retains the final decision. The
same AI suggestion and student context are available during advisor review and
HOD final sign-off.

CampusRent listings use the `marketplace_products` SQLAlchemy table in
`complaints.db`. The repeatable seeder creates 100 synthetic product listings;
it can be run manually with `uv run python seed_marketplace_products.py` and
the API also seeds the catalog on startup if the table is empty. The marketplace
frontend combines these database listings with its existing browser-local demo
listings. `POST /api/marketplace/chat` searches the available database catalog
and sends matching listing details to the Sarvam-105B agent. Recommendations
reference database product IDs only. Students can open a recommended listing,
choose rental dates, and submit through the existing rental-request form; the
request remains in the current browser-local demo store. The assistant cannot
place requests or process payments.
